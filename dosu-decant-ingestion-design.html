Ingesting AI Coding-Agent Sessions into Dosu

A design dossier: how to turn ephemeral, laptop-trapped Claude Code / Codex sessions into durable, citable team knowledge inside Dosu — grounded in a four-angle codebase audit and Exa deep research.

Status: design (draft) Distill-first Full build · phased 0/1/2 2026-06-07 · onlydole + Claude

01 — Executive summary

The one-paragraph version

Today the richest record of why a team builds what it builds — the decisions, the dead-ends, the bug that cost three hours and one config flag — evaporates when a terminal closes. decant already captures it locally (every Claude Code and Codex session, normalized into SQLite). Dosu makes connected knowledge answerable. This design connects the two: a new Dosu data source fed by decant, so a team can ask Dosu “why did we move the writer to WAL mode?” and get a cited answer drawn from a past agent session.

Recommended direction

Distill-first, phased. decant distills each session locally into verifiable, redacted, typed artifacts (decisions, gotchas, how-tos, Q&A); only those cross the wire. Raw transcripts never become the primary citable layer — they stay in decant, surfaced (if at all) as review-gated evidence. Ship a zero-schema Phase 0 (distilled pages via the existing Pages API) to de-risk transport & redaction, then build the first-class typed entity (Phase 1) and optional raw evidence (Phase 2).

This is decisive because the goal — helping users surface durable information — is far better served by high-signal distilled knowledge than by raw-transcript recall, and it is dramatically safer given that redaction is best-effort with no server-side backstop.

02 — Goal & scope

What we’re building (and not)

Goals

  1. Turn ephemeral, per-laptop agent sessions into durable, org-searchable, citable knowledge inside Dosu’s existing ask / chat / search surfaces.
  2. Maximize signal: a retrieved answer is a real decision / fix / how-to mapped to a verifiable artifact (a commit, a passing test, a concrete diff) — not transcript noise.
  3. Preserve privacy: secrets & PII in shell output never reach a multi-tenant index.
  4. Ground knowledge to code (repo / branch / commit) so staleness is trackable.

Non-goals (v1)

  • No verbatim transcript search in Dosu. Raw transcripts stay in decant’s local reader.
  • No new Nango/OAuth connector. Transport reuses Dosu’s existing authenticated inbound push seams.
  • No per-repo / per-author ACL. v1 relies on Dosu’s org-scoped RLS (documented gap).
  • No continuous sync. Push is on-demand, idempotent on a content hash.
  • No v2/Turbopuffer-only path. Production retrieval reads v1 LanceDB today.

04 — Audit

How Dosu ingests today

Source of truth: ~/dosu/dosu — a Python backend/ monolith on DBOS workflows, Supabase Postgres, Next.js frontend, Pulumi/GCP deploy. Produced by a four-angle code audit, independently re-verified.

Data-source model

  • Sources keyed by ProviderSlug (backend/core/db/sql/models.py:329): GitHub, Slack, Notion, Confluence, Coda, GitLab, Web, Linear, Jira, Teams, plus internal MEMORY, DOSU_KNOWLEDGE_STORE, DOSU_MCP, DOSU_APP.
  • public.data_source: wide, org-scoped (RLS by org_id), one nullable FK per provider; enabled / is_indexed flags. Base class DataSource with a to_provider_type() dispatch hub.
  • All existing sources are cloud SaaS, connected via Nango OAuth and synced server-side by scheduled DBOS workflows. Credentials live in Nango, never local.
  • ProviderSlug.MEMORY is dead code — an abandoned LangMem spike. No shortcut.

Indexing pipeline

  • Two vector stores mid-migration: v1 LanceDB (authoritative) + v2 Turbopuffer (forward path), dual-write gated by a PostHog flag. v2 runs with skip_mark_indexed=True, so v1 owns the indexed-version field by design.
  • Embeddings: v2 = Voyage voyage-4-large (1024-dim); v1 = OpenAI text-embedding-3-small (1536-dim). Redis-cached.
  • Chunking: CONTENT_CHUNK_SIZE = 2048 characters, overlap 0. PRs are a single chunk (title + body + LLM summary), embedding only the summary.
  • LLM enrichment at index time already exists: PR summarization, topic assignment, v1 synthetic “what questions does this file answer?” docs.
  • Freshness: a 5-minute incremental cron diffs data_source_entity fingerprints (XOR of md5 hashes); unchanged entities skipped; re-index is an atomic replace.

Knowledge schema

  • public.document_source is the central provenance table: an entity_type discriminator + one nullable FK per type, a one_source_check CHECK, and trigger functions that set title/external_url via a hard ELSE RAISE EXCEPTION switch. This is the real schema blocker.
  • knowledge.question_answer = AI-synthesized Q&A pairs derived from threads (the distillation precedent). public.citation carries source/url/title/line-range/data_source_id. Plus topic, page/page_version, knowledge_store, libraries (space).

Retrieval & surfacing

  • The production ask agent (Claude Sonnet) calls per-source-type search tools (search_threads, search_documentation, …) → an HTTP search service.
  • Everything surfaced becomes a CitableSource {data_source_id, source_type, title, url, content, created_at?, summary?, start_line?/end_line?}; cited inline as (cite:source_type:hex8[:line]) and rewritten to links; hallucinated cites stripped.
  • The search path is a chain of closed enums/dicts; miss one and a new type is silently unreachable. LDBTable.MESSAGE is semantic-only (no BM25); QUESTION_ANSWER and PAGE get {Semantic, FullText}.

05 — Verification

Four claims the design rested on — checked against the live repo
Correction 1 — retrieval is in-repo, not a black box

The search service is an in-repo, co-deployed Cloud Run microservice (backend/search/, deployed by deploy/cloudrun.go) — not an external Cloud Function. All changes are in-repo. But the closed-enum chain (LDBTable → registry maps → TABLE_NAME_TO_STRATEGIES → per-endpoint Search lists → SUPPORTED_*_LDB_TABLES) must be updated completely — fail-silent otherwise.

Correction 2 — v1 LanceDB is the only production-readable store

v2/Turbopuffer search tools (search_v2/, threads_search, …) are imported only in tests; search/router.py _validate_data_source 404s a source with no LanceDB directory. → Target v1. (THREAD/PAGE are already in _V2_ENABLED_ENTITIES, so dual-write is free later.)

Correction 3 — the thread→Q&A distillation precedent is real, but with a catch

A 30-minute DBOS cron (extract_new_qa_pairs) distills any resolved=true thread from any enabled source into knowledge.question_answer — no provider filter (hence E7: we keep agent sessions out of it). MEMORY is a dead stub.

Correction 4 — transport needs no new connector

Existing authenticated inbound paths: the Pages API (POST /v1/deployments/{id}/pages), MCP save_topic, and the CLI-auth ticket flow (POST /v1/cli/auth/tickets). The “commit a .dosu/ file and let Dosu’s git sync ingest it” idea is blocked — that store is contained to Dosu’s own Filestore.

06 — Source

decant’s data model & the offline constraint

decant archive (crates/decant-core/src/schema_v1.sql): project → session (tool, cwd, git_branch, model, timestamps, token/cost totals) → message (role, seq) → block (type ∈ text|tool_use|tool_result; text, tool_name, tool_input, tool_result); a normalized tool_call table (tool_kind, tool_base_name, mcp_server, is_error, output_preview, duration_ms); block_fts (FTS5). Rich, structured, timestamped transcripts with a code anchor — and potential secrets/PII in shell output.

E6: session will also capture head_commit_sha for valid_as_of_commit grounding — a small decant-core parser/schema change.

The offline-invariant constraint (E3)

decant’s invariant: “Don’t add network calls to decant-core or the CLI; decant is a local-first, offline tool.” Distillation (an LLM call) and push (to Dosu) are both network — so they cannot live in decant-core/decant-cli.

crates/decant-core   offline: parse + normalize + read; UI-agnostic     ← unchanged
crates/decant-cli    offline: sync/ls/search; all stdout/exit policy    ← unchanged
crates/decant-dosu   NEW, networked: read archive → distill → redact → push

The offline archive stays offline; the export to Dosu is a separate, opt-in binary that depends on decant-core read-only. Rejected alternative: distill server-side — it would require shipping raw transcripts off the laptop, defeating E2.

07 — Research

What the field already knows (Exa deep research)

Principles applied to this design — full citations in §22.

  • Distill, don’t dump. Memory systems (Mem0, Zep, Letta/MemGPT) extract salient facts and add/update/supersede rather than storing raw turns; promote to durable only against a verifiable artifact. Treat ephemeral tool output and chain-of-thought as transient.
  • Typed extraction. Decision/rationale mining → typed decision records; auto Q&A/FAQ; “lesson/gotcha” claim extraction via trigger phrases (“don’t do”, “we had to”, “broke because”, “the fix was”), validated against commits/tests.
  • Segment into interaction units (a user prompt + its assistant turns + the tool-call cluster + result) before extraction.
  • Dedup / novelty. Merge near-duplicates (cosine ≥ ~0.92) rather than re-adding; novelty = inverse similarity to prior items for the same repo. Prevents memory bloat.
  • Hybrid retrieval (vector + BM25) matters for exact tokens — error strings, symbols, flag names — exactly what developers ask agent history about.
  • Tiered redaction before indexing: key-based → regex → entropy/format → NER/LLM; enforce ACL at retrieval time (no-access = no-result).
  • Ground to code & track staleness (EntireContext, Lore): anchor to repo/file/commit; valid_as_of_commit + timestamp; flag stale when the linked file’s commit diverges; supersede, don’t delete.
  • RAG failure modes to design against: hallucinated authority, stale advice, conflicting answers across sessions, permission leakage, no-answer blindness — each with a concrete mitigation (§18).

08 — Exploration

Three competing designs, independently judged

A multi-agent design workflow generated three end-to-end designs from distinct stances and scored each through three lenses (Dosu-fit/effort, knowledge value/retrieval, risk/privacy). The recommendation grafts the winners together.

Design A

Raw transcripts as threads

Model each session as a Dosu thread; index raw turns; ride the thread pipeline + free Q&A cron. Cheapest, maximal reuse.

Weakness: chatty, semantic-only (no BM25) raw turns pollute the index and collapse every citation to “Thread”.

Design B

Knowledge Distillery

Distill locally into typed artifacts behind a verifiable-artifact gate; never index transcripts. Highest signal & privacy.

Weakness: walks straight into the schema/trigger blockers + a synthetic-thread smell.

Design C

Hybrid, phased

Distilled pages first (zero schema), native entity later, raw chunks as parent-child evidence. Sequenced de-risking.

Weakness: taken to completion it’s the widest net-new surface.

How they scored

FitValueRisk
A★★★★★★★★★★★★★★★
B★★★★★★★★★★★★★★★
C★★★★★★★★★★★★★★★

Fit = Dosu-fit/effort · Value = knowledge/retrieval · Risk = risk/privacy

The synthesis: take B’s discipline (distill first, verifiable-artifact gate, redact the artifact) and C’s sequencing (zero-schema Phase 0 to de-risk), realized through a first-class typed entity. Design A’s “index raw turns” default is rejected.

The four biggest forks

  1. Citable layer: distilled artifacts only (chosen) vs raw turns as primary (rejected).
  2. Surfacing seam: PAGE (Phase 0) → typed entity (Phase 1) → parent-child evidence (Phase 2), each paid for only when measurement proves the prior insufficient.
  3. Transport: existing CLI-auth + Pages/thin-ingest endpoint (chosen) vs a new Nango connector (rejected) vs the .dosu-committed-file path (blocked).
  4. Q&A-cron coupling: keep agent sessions out of extract_new_qa_pairs (E7) so dead-end sessions never pollute durable Q&A.

Open questions still worth a conscious answer

  • How aggressive is the verifiable-artifact gate (precision vs recall dial)?
  • Per-repo / per-author ACL — accepted as a v1 gap, but when must it land before broad rollout?
  • Confirm decant-dosu as a deliberate, documented exception to the offline invariant (E3).

11 — Distillation

The local pipeline (decant-dosu)

Per session: filter → segment → extract → validate → dedup.

  1. Filter (cheap heuristics): drop low-signal sessions — no git_branch, < N assistant turns, zero file-mutating tool calls.
  2. Segment into interaction units by message.seq + block.ordinal + tool_call.ordinal → (user prompt, assistant turns, tool-call cluster, result). decant’s normalized tool_call makes code-mutating units (Write/Edit/Bash-git/apply_patch) detectable.
  3. Extract (LLM) typed artifacts via trigger-phrase mining + staged draft→evaluate→revise:
    • Decision { title, decision, rationale, alternatives_rejected }
    • QAPair { title, question, answer }
    • LessonGotcha { claim, context, remedy }
    • HowTo { title, steps }
  4. Validate — the E4 gate: promote to durable only if mapped to a verifiable artifact in the same session — a git commit SHA, a passing/non-error test (tool_base_name ∈ {pytest, cargo test, …}, is_error=0 after the change), or a concrete file diff. Unanchored candidates stay transient and are never pushed. If the repo isn’t a connected Dosu source, don’t promote.
  5. Dedup / supersede (local state in decant.db): cosine ≥ ~0.92 against prior pushed artifacts for the same repo ⇒ merge; a newer contradicting artifact sets the old one’s superseded_by (never destructive).

decant-core invariant respected: distillation returns typed Rust structs + Results; the LLM call, printing, and push all live in decant-dosu.

12 — Redaction

The single most safety-critical component

Runs on the laptop, on the distilled artifact (not the transcript), before any push — there is no server-side redaction on the ingest path, so the laptop is the only safe gate.

  1. Key-based drop of known-secret env names (AWS_*, *_TOKEN, *_SECRET, *_KEY) and reads of secret-glob paths (.env, *.pem, credentials).
  2. Regex: PEM blocks, JWTs, sk-…/gh[ps]_… tokens, connection strings, emails.
  3. Entropy/format detectors over residual high-entropy tokens.
  4. NER/LLM pass for residual PII (cheap — the artifact is already ~100× smaller than the transcript).
Treat a redaction false-negative as Sev-1

decant-dosu push --dry-run prints exactly what would leave the machine. Server-side defense-in-depth: a reject-on-detected-secret check before write. Phase-2 raw evidence gets the same redaction and is review-gated (D2). ACL is enforced at retrieval by Dosu’s org-scoped RLS (no-access = no-result).

13 — Transport

No new connector
  • Auth: decant-dosu runs the existing CLI-auth ticket flow (POST /v1/cli/auth/tickets → /bind → /exchange) for a Supabase JWT without a localhost callback, stored next to the local DB; or a long-lived MCP sk_user_* API key.
  • Ingest — Phase 0: POST /v1/deployments/{id}/pages (one markdown page per artifact; distilled artifacts publish as searchable per D2 — --dry-run is the safety control), anchor metadata in page.description.
  • Ingest — Phase 1+: a thin POST /v1/deployments/{id}/agent-sessions endpoint cloned from create_page (same auth, RLS, user_can_write) accepting {session_meta, artifacts[], evidence_chunks[]?} and writing the native rows.

Push is idempotent on a content hash of (source_session_id, artifact_kind, normalized_text) — re-pushing an unchanged archive is a no-op, mirroring decant’s size+mtime sync skip.

15 — Indexing

Target v1 LanceDB

Distilled artifacts are short ⇒ one chunk each (title + body + answer), like the PR-summary precedent — we never run the 2048/0 splitter on raw transcript. Add a contextual-embedding prefix (anchor file path + kind label) before embedding.

New wiring — the closed-enum chain (all required, or the source is silently unsearchable):

  • LDBTable.AGENT_SESSION_ARTIFACT + an AgentSessionArtifactDocument registered in TABLE_DOCUMENT_TYPE_MAP, TABLE_SEARCH_FIELD_MAP (openai_3_small_embedding, 1536-dim), ENTITY_TYPE_TABLE_MAP, the LDBDocumentType union.
  • EntityLoaderProto exposing diff_version = hash(text + anchor + staleness_status) so supersede/refresh re-indexes; EntityDBClientProto; DocumentGeneratorProto; a get_agent_session_worker() + get_worker() branch.
  • Optional, free later: add to _V2_ENABLED_ENTITIES + a v2 ContentType + Turbopuffer namespace — skip until v2 retrieval is promoted to production.

16 — Retrieval

Surfacing in ask
  • Search service: add LDBTable.AGENT_SESSION_ARTIFACT to TABLE_NAME_TO_STRATEGIES with {SemanticSearch, FullTextSearch} (BM25 is what makes error-string/symbol/flag queries work); add a search_agent_sessions() method + /agent-sessions route (or extend search_threads).
  • Agent: add a search_agent_sessions tool into the ask agent’s tool list; add ProviderSlug.AGENT_SESSION → {LDBTable.AGENT_SESSION_ARTIFACT} to SUPPORTED_*_LDB_TABLES so the runtime probe selects the source.
  • Citations: results become CitableSource{source_type='agent_session', title, url=decant deep link or repo anchor, content, summary, start_line?/end_line?}; cited (cite:agent_session:hex8[:line]); gated at relevance_score ≥ 0.4.
  • Phase 2 parent-child: the artifact is the parent (ranked); redacted raw interaction-unit chunks are children expanded via /retrieve-context — verbatim evidence without polluting primary ranking.

17 — Grounding & staleness

Anchored to code, superseded over time

Each artifact carries a code anchor from decant’s real columns: cwd + git_branch + head_commit_sha (E6) ⇒ repo_slug, git_branch, valid_as_of_commit. On push, the ingest endpoint resolves anchor_file_paths to GITHUB_FILE document ids in the same org and sets code_document_ids — the same field Dosu’s existing stale-knowledge machinery uses. When a linked file’s latest indexed commit diverges from valid_as_of_commit, staleness_status flips fresh → stale; a newer contradicting artifact sets superseded_by + status superseded (auditable, never destructive). external_url deep-links back to the raw decant session — evidence lives only on the laptop.

19 — Build sequence

Order of operations
  1. Phase 0 (decant-side, ~2–3 wk): the decant-dosu crate — read → distill → E4 gate → redact → CLI-auth → POST /pages. Zero Dosu schema; same-day searchable. Proves transport + redaction + distillation.
  2. Phase 1 (Dosu-side, ~4–6 wk): provider + typed entity migration (§14) + indexing (§15) + retrieval (§16) + grounding (§17) + the /agent-sessions endpoint. High blast radius — single migration, rehearsed, with the e2e retrieval test as DoD.
  3. Phase 2 (~2–3 wk): redacted raw interaction-unit evidence chunks as review-gated parent-child evidence.

Testing

  • decant-dosu (Rust, TDD): unit-test segmentation, the E4 gate (committed vs abandoned session fixtures), redaction (planted secrets must not survive), dedup/supersede; snapshot the push payload.
  • Dosu (Python): migration test asserting all four trigger arms + the CHECK; loader/document-generator unit tests; the e2e retrieval integration test as DoD.
  • Eval pass: a labeled query set measuring precision/recall of distilled answers vs a raw-transcript baseline — gates whether Phase 2 is needed and tunes the gate.

20 — Risks & deferred

Known gaps, eyes open
  • Per-repo / per-author ACL is a real gap (D3). v1 is org-wide; must be revisited before broad multi-team rollout. Author tagging is recorded now to enable later filtering.
  • Transport is manual & per-developer (decant-dosu push). Coverage = whoever runs it; no continuous sync (a deliberate v1 non-goal).
  • Redaction is best-effort with no server backstop — the single most safety-critical component; misses are Sev-1.
  • decant-core offline-invariant exception (E3) — confirm the decant-dosu crate approach.
  • Migration blast radius (§14) — non-transactional ALTER TYPE + trigger surgery on a live multi-tenant DB; rehearse, single migration, migration test.
